# BUG-003 — Migração 0005 (T012) quebra em Postgres real: `ALTER COLUMN ... SET DATA TYPE bigserial` é SQL inválido

## Status
PRONTO PARA RETESTE

## Correção aplicada
`drizzle/0005_small_captain_america.sql` — o `ALTER COLUMN "id" SET DATA TYPE bigserial` foi substituído pela expansão manual real de `bigserial` (hipótese técnica do próprio bug): `DROP DEFAULT` → `ALTER COLUMN ... TYPE bigint USING NULL` (tabela sem dado real, troca segura) → `CREATE SEQUENCE` própria → `SET DEFAULT nextval(...)` → `SET NOT NULL`. Constraint de PK original (`extracoes_orcamento_historico_pkey`) nunca foi tocada — segue válida durante toda a troca de tipo.

Validado localmente: `drizzle-kit generate` (0000→0006) aplicado do zero contra Postgres 16 real (container `pgvector/pgvector:pg16` limpo, porta efêmera) sem erro; suíte `extracao-orcamento.schema.test.ts` — 7/7 passando contra esse banco (antes: 5 falhas); `npx drizzle-kit generate` sem diff pendente após a correção (schema TS inalterado, só o SQL manual da migração 0005 mudou).

## Resumo
A migração `drizzle/0005_small_captain_america.sql`, gerada por `drizzle-kit generate` para evoluir `extracoes_orcamento_historico.id` de `uuid` (baseline T002, migração 0003) para `bigserial` (T012), emite:

```sql
ALTER TABLE "extracao"."extracoes_orcamento_historico" ALTER COLUMN "id" SET DATA TYPE bigserial;
```

`bigserial` não é um tipo de coluna válido para `ALTER COLUMN ... SET DATA TYPE` — é um pseudo-tipo que só existe no contexto de `CREATE TABLE` (onde se expande em `bigint` + sequência + `DEFAULT nextval(...)`). O Postgres rejeita o comando com `ERROR: type "bigserial" does not exist`. A migração para no primeiro statement, nenhuma das colunas subsequentes de `extracoes_orcamento`/`extracoes_orcamento_historico` é criada.

Isso quebra `drizzle-kit migrate` em qualquer ambiente partindo do baseline (T002) — incluindo o step `pnpm run db:migrate` do CI (`.github/workflows/ci.yml:63`), que roda antes da suíte de testes.

## Pré-condições
- Banco em estado pós-T002 (baseline): `extracoes_orcamento_historico.id` já existe como `uuid`.
- Rodar `pnpm run db:migrate` (ou `npx drizzle-kit migrate`) com `DATABASE_URL` apontando para esse banco.

## Resultado atual
`drizzle-kit migrate` falha (exit 1) e nenhuma das novas colunas de T012 é criada em nenhuma das duas tabelas. `extracoes_orcamento_historico.id` permanece `uuid NOT NULL` (do baseline), incompatível com o schema TS (`bigserial('id', { mode: 'bigint' })`), causando falhas de `NOT NULL constraint` em qualquer INSERT sem `id` explícito.

## Hipótese técnica
`drizzle-kit generate` calcula o diff de tipo de coluna (`uuid` → `bigserial`) e emite um `ALTER COLUMN ... SET DATA TYPE` literal usando o nome do tipo Drizzle (`bigserial`) em vez de expandir para `bigint` + criar sequência + `SET DEFAULT nextval(...)` + `OWNED BY`, que é o que `bigserial` realmente significa em DDL do Postgres. É uma limitação conhecida de `drizzle-kit` ao gerar diff para mudança de tipo de PK usando o pseudo-tipo `serial`/`bigserial` em coluna já existente — só funciona corretamente em `CREATE TABLE` novo (que é o caso de 0006 em diante, não o de uma coluna herdada do baseline T002). Mesmo padrão de risco documentado no comentário do schema (linha 61-64: "a garantia de imutabilidade vem da migração SQL, nunca confiar só na disciplina do repositório") se aplica aqui à geração automática: migrações de mudança de tipo de PK precisam ser conferidas manualmente antes do merge, não apenas geradas e commitadas.
