# BUG-001 — URL presigned de upload é inutilizável: SDK assina `x-amz-checksum-crc32` de corpo vazio, e o PUT real é rejeitado com 400

## Status

ABERTO — reproduzido de forma determinística; correção **não** aplicada em código de produção.

## Severidade

CRÍTICA

## Prioridade sugerida

P0

## Origem

- SPEC_ID: 001-ingestao-classificacao-orcamentos
- Requisito: T021/#26 (`POST /v1/orcamentos/upload-url`) + ADR-002 (upload via presigned URL em vez de multipart no API Gateway)
- Critério de aceite: a URL devolvida por `POST /upload-url` deve aceitar o `PUT` do arquivo pelo cliente — é o primeiro passo do canal principal de US1
- Tarefa: T019/#24 (`S3ArmazenamentoBrutoGateway`), consumido por T021/#26
- Ambiente: LocalStack 3.8.1 (S3), bucket `nexo-orcamentos-raw` com Object Lock + versionamento, `@aws-sdk/client-s3` ^3.1097.0 / `@aws-sdk/s3-request-presigner` ^3.1099.0, Node 24.14.1
- Commit ou versão: descoberto ao montar a execução local do fluxo 001→002 (T067/#589)

## Resumo

`S3ArmazenamentoBrutoGateway.gerarUrlUpload` (`src/bounded-contexts/ingestao-identificacao/infrastructure/s3-armazenamento-bruto.gateway.ts`) presigna um `PutObjectCommand` via `getSignedUrl`. Nas versões de 2025 em diante, o AWS SDK v3 tem `requestChecksumCalculation: 'WHEN_SUPPORTED'` como default e adiciona checksum a todo `PutObject`.

No momento da assinatura o SDK não tem o corpo do objeto — quem envia os bytes é o cliente, numa requisição posterior. Ele então calcula o checksum do corpo que conhece (vazio) e embute o resultado na query string **e dentro da assinatura SigV4**:

```
?...&x-amz-checksum-crc32=AAAAAA%3D%3D&x-amz-sdk-checksum-algorithm=CRC32&...
```

`AAAAAA==` é o base64 de quatro bytes zero — CRC32 de conteúdo vazio. A URL passa a declarar, de forma assinada e imutável, "o corpo deste PUT tem CRC32 de vazio". Quando o cliente faz o `PUT` com o arquivo real, o S3 calcula o checksum recebido, compara com o declarado e rejeita a requisição com **400**.

Efeito prático: **toda** URL gerada por `POST /v1/orcamentos/upload-url` é inutilizável para arquivo não vazio. US1 quebra no primeiro passo do canal principal (`PORTAL_WEB`, `API_REST`, `APP_MOBILE`); só o canal SFTP escapa, porque não passa por presigned URL (ADR-002).

Não é particularidade do LocalStack: validação de checksum de request é comportamento normal do S3. O mesmo bucket na AWS real rejeita igual.

## Pré-condições

- Bucket `nexo-orcamentos-raw` existente, com versionamento e Object Lock (como criado pela `IngestaoIdentificacaoStorageStack`).
- `S3Client` construído **sem** `requestChecksumCalculation` explícito — isto é, com o default do SDK.

## Passos para reproduzir

1. Subir Postgres + LocalStack, migrar o banco e criar bucket/bus/filas (ver T067/#589).
2. `POST /v1/orcamentos/upload-url` com `{"canal":"API_REST","nomeArquivo":"orcamento.txt"}`.
3. Inspecionar a `uploadUrl` da resposta: contém `x-amz-checksum-crc32=AAAAAA%3D%3D` e `x-amz-sdk-checksum-algorithm=CRC32`.
4. `curl -X PUT --upload-file orcamento.txt "<uploadUrl>"` com qualquer arquivo de conteúdo não vazio.
5. Resposta: **HTTP 400**. O objeto não é gravado.
6. Consequência em cascata: `POST /{orcamentoId}/confirmar-upload` responde `409 upload-nao-concluido` (o `HeadObject` da chave pendente não encontra nada), e o orçamento nunca é criado.

## Resultado atual

`PUT` na URL presigned devolve 400 para qualquer corpo não vazio. Nenhum objeto chega ao bucket; `confirmar-upload` devolve 409 e o fluxo de US1 não avança.

## Resultado esperado

`PUT` na URL presigned devolve 200 e grava o objeto com `VersionId`, permitindo que `confirmar-upload` encontre a chave pendente e dispare `ReceberOrcamento`.

## Evidências

Execução local, mesma chamada antes e depois de configurar o client:

```
# S3Client com default do SDK (requestChecksumCalculation: WHEN_SUPPORTED)
2) PUT presigned: http=400
3) confirmar-upload: {"type":"https://nexo.internal/problems/upload-nao-concluido",
                      "title":"Upload ainda não concluído para este orcamentoId","status":409}

# S3Client com requestChecksumCalculation: 'WHEN_REQUIRED'
2) PUT presigned: http=200
3) confirmar-upload: {"orcamentoId":"019fc857-d99e-7fec-8820-4cc060c8c87b"}
4) status: {"status":"CLASSIFICADO", ...}
```

URL presigned gerada no caso com defeito (trecho, assinatura truncada):

```
http://localhost:4566/nexo-orcamentos-raw/pending-uploads/019fc855-...-orcamento.txt
  ?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Signature=6995d1d7...
  &x-amz-checksum-crc32=AAAAAA%3D%3D&x-amz-sdk-checksum-algorithm=CRC32
  &x-amz-object-lock-mode=GOVERNANCE
```

Nenhum dado sensível envolvido — arquivo de teste com conteúdo fictício, credenciais do LocalStack (`test`/`test`).

## Frequência

SEMPRE — determinístico. Independe de tamanho ou tipo de arquivo; só corpo vazio passaria.

## Impacto

- Bloqueia US1 nos 3 canais de upload via API (`PORTAL_WEB`, `API_REST`, `APP_MOBILE`).
- Bloqueia, por consequência, US2/US4/US5 e toda a spec 002: sem orçamento recebido, nada é classificado nem extraído.
- Não afeta o canal SFTP (T023/#28), que não usa presigned URL.
- Não afeta `confirmarUpload` em si (usa `CopyObject`, server-side, sem corpo) nem a leitura de bruto em 002 (`GetObject`, sem checksum de request).

## Hipótese técnica

O `S3Client` é injetado por construtor — o gateway não o cria e portanto não controla essa configuração. A correção pertence a quem constrói o client, e hoje **ninguém** constrói: não existe composition root de produção no repositório (zero `export const handler`, zero `lambda.Function` em `infra/lib/`). O defeito ficou latente porque nunca houve um `PUT` real contra a URL gerada: os testes de contrato de T021/#26 verificam o formato da resposta (`orcamentoId` + `uploadUrl` válida), não o upload de fato.

Correção em duas partes:

1. `requestChecksumCalculation: 'WHEN_REQUIRED'` no `S3Client` usado no caminho de upload, com o requisito documentado no doc-comment de `gerarUrlUpload` — é lá que a próxima pessoa vai olhar.
2. Guarda de regressão: teste que presigna com `S3Client` de configuração default e afirma que a URL **não** contém `x-amz-checksum-`. Falha hoje, passa após a correção. Sem essa guarda, um upgrade de SDK ou um client novo em outro caminho reintroduz o problema em silêncio.

## Escopo de regressão sugerido

Após a correção: exercitar o fluxo real `upload-url` → `PUT` → `confirmar-upload` → `status` (não apenas os testes de contrato) e confirmar 200 no `PUT` e criação do orçamento. Rodar a suíte completa. Revisar se algum outro caminho futuro presigna `PutObject` (nenhum hoje além deste).

## Escopo entregável e critério de fechamento

Este bug **não fecha sozinho**. Divisão explícita:

**Entregável agora (independente de qualquer outra task):**

1. Documentar o requisito no doc-comment de `gerarUrlUpload`: o `S3Client` injetado MUST vir com `requestChecksumCalculation: 'WHEN_REQUIRED'`.
2. Guarda de regressão: teste que presigna com `S3Client` configurado `WHEN_REQUIRED` e afirma que a URL **não** contém `x-amz-checksum-`. Verde hoje; quebra se o SDK mudar de default ou se alguém remover a configuração. A variante "presignar com client default e esperar URL limpa" não é mergeável — falharia hoje, porque o defeito está no default do SDK, não em código deste repositório.

**Gate para a futura task de composition root / handler Lambda:**

3. Aplicar a configuração no ponto real de construção do `S3Client` de produção. Não há onde fazer isso hoje (nenhum `export const handler`, nenhum `lambda.Function` em `infra/lib/`), e essa lacuna não tem issue própria.

**Critério de fechamento**: itens 1 e 2 mergeados **e** evidência de `PUT` HTTP 200 numa URL presigned gerada pelo código de produção contra bucket versionado real.
