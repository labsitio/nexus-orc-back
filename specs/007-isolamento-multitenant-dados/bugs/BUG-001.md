# BUG-001 — `DrizzleOrcamentoRepository.buscarPorId` nunca reconstrói `tenantId` do agregado

## Status
ABERTO

## Severidade
ALTA

## Prioridade sugerida
P1

## Origem
- SPEC_ID: 007-isolamento-multitenant-dados (retrofit `tenantId`, ADR-008)
- Requisito: `Orcamento.tenantId` reconstituído a partir da coluna persistida em toda leitura (padrão já aplicado nos outros 4 BCs)
- Critério de aceite: nenhum agregado deveria ser tratado como "pré-retrofit" (`tenantId` ausente) após a conclusão do retrofit multi-tenant
- Tarefa: achado durante validação de QA da PR #715 (ambiente de desenvolvimento local, `feat/dev-ambiente-local-002-a-005`) — bug é de código de produção do BC `ingestao-identificacao` (spec 001), não desta PR
- Ambiente: local (Postgres real via docker-compose, sem RLS desabilitada), reproduzível também em qualquer ambiente com Postgres real
- Commit ou versão: `main` atual (`19356a0`), também presente no branch da PR #715 (`4049a4e`) — não introduzido por ela

## Resumo

`agregadoDaLinha` em `src/bounded-contexts/ingestao-identificacao/infrastructure/persistence/drizzle-orcamento.repository.ts` (função privada usada por `buscarPorId`) monta `OrcamentoProps` sem o campo `tenantId`, mesmo a coluna `orcamentos.tenant_id` estando preenchida (é `NOT NULL`, gravada em `salvar`). O equivalente nos outros 4 BCs (`extracao`, `validacao`, `busca-indexacao`, `orquestracao`) inclui `tenantId: TenantId.de(linha.tenantId)`. Resultado: toda leitura pós-criação de um orçamento no BC 001 devolve um agregado com `tenantId` `undefined`.

O guard de retrofit em `classificador-queue.handler.ts` (ou código equivalente que consome o agregado) interpreta `tenantId` ausente como "registro pré-retrofit" e ignora a mensagem como sucesso idempotente, sem publicar `OrcamentoClassificado`. Efeito em cascata: a classificação nunca acontece, e o próprio `GET /v1/orcamentos/{id}/status` do BC 001 (que também lê via `buscarPorId`) não encontra o orçamento (embora a linha exista no banco) — na prática hoje ele devolve 404 por outro caminho de leitura, mas o efeito de fundo (tenantId ausente no agregado) é o mesmo bug.

## Pré-condições
- Postgres real rodando (RLS scoping ativo via `DrizzleTenantScopedRepositoryBase`)
- Um orçamento já persistido via `POST /v1/orcamentos/{id}/confirmar-upload` (ou `ReceberOrcamento` diretamente)

## Passos para reproduzir
1. Subir ambiente local: `pnpm docker:up && pnpm db:migrate && pnpm dev:seed && pnpm dev` (branch da PR #715, mas reproduz igual em `main`)
2. `POST /v1/orcamentos/upload-url` com `{"nomeArquivo":"orcamento-teste.txt","canal":"PORTAL_WEB"}` → 201, capturar `orcamentoId` e `uploadUrl`
3. `PUT` do conteúdo texto na `uploadUrl` (presigned S3) → 200
4. `POST /v1/orcamentos/{orcamentoId}/confirmar-upload` com `{"canal":"PORTAL_WEB","nomeArquivo":"orcamento-teste.txt"}` → 200
5. Aguardar o poller `classificador-queue` consumir a mensagem (alguns segundos)
6. Observar o log: `"motivo":"AUSENTE"`, `"msg":"Orçamento sem tenantId no agregado (registro pré-retrofit) — ignorado como sucesso idempotente"`
7. `GET /v1/orcamentos/{orcamentoId}/status` → 404 "Orçamento não encontrado" (mesmo com a linha existindo na tabela `orcamentos`)

## Resultado atual
`tenantId` do agregado reconstituído por `buscarPorId` é sempre `undefined`, independente do valor real gravado na coluna. Classificação nunca ocorre; leituras subsequentes tratam o orçamento como inexistente.

## Resultado esperado
`agregadoDaLinha` deveria reconstituir `tenantId: TenantId.de(linha.tenantId)`, igual ao padrão já usado nos repositórios equivalentes de `extracao`, `validacao`, `busca-indexacao` e `orquestracao` (ver `DrizzleExtracaoOrcamentoRepository`, linha 119: `tenantId: TenantId.de(linha.tenantId)`).

## Evidências
- teste automatizado: nenhum teste unitário/integração cobre hoje que `buscarPorId` reconstitui `tenantId` corretamente para o BC 001 (os 4 outros BCs têm esse assert — confirmar lacuna específica é ação de continuação do dev-back-end/QA numa correção futura)
- execução: log real capturado em smoke test manual (ambiente local, Postgres via docker-compose), reproduzido nesta validação de QA
- logs sanitizados:
  ```
  {"level":30,"handler":"classificador-queue","orcamentoId":"019fee41-1643-7d7b-8107-b9e4fba7ebde","tenantId":"018f4a3c-0000-7000-8000-000000000001","msg":"Classificando orçamento"}
  {"level":40,"handler":"classificador-queue","orcamentoId":"019fee41-1643-7d7b-8107-b9e4fba7ebde","motivo":"AUSENTE","tenantIdSolicitante":"018f4a3c-0000-7000-8000-000000000001","msg":"Orçamento sem tenantId no agregado (registro pré-retrofit) — ignorado como sucesso idempotente"}
  ```
  (`tenantId` no log é o UUID v7 fixo de dev configurado em `NEXO_LOCAL_TENANT_ID`/`.env` — não é dado sensível)
- payload/resposta sanitizados: `GET /v1/orcamentos/{orcamentoId}/status` → `{"type":"https://nexo.internal/problems/nao-encontrado","title":"Orçamento não encontrado","status":404}`

## Frequência
SEMPRE — toda leitura de orçamento via `buscarPorId` no BC 001, em qualquer ambiente com Postgres real.

## Impacto
Bloqueia a progressão real do pipeline 001→005 (classificação nunca publica `OrcamentoClassificado`, então extração/validação/indexação/decisão de workflow nunca são acionadas para nenhum orçamento). Não é um bug do ambiente local — a mesma leitura ocorre em produção; só nunca foi exercitada localmente porque o runner local não tinha tenant context nenhum antes da PR #715 (toda rota gated devolvia 401).

## Hipótese técnica
Comparação direta de código confirma a causa: `agregadoDaLinha` (BC 001) omite `tenantId` no `OrcamentoProps` retornado; o equivalente nos outros 4 BCs inclui `tenantId: TenantId.de(linha.tenantId)`. Não é hipótese — é diferença de código verificável lendo os dois arquivos lado a lado.

## Escopo de regressão sugerido
Após a correção: reexecutar o smoke test completo 001→005 descrito acima e confirmar que `GET /v1/orcamentos/{id}/status` (001) reflete o status real e que `OrcamentoClassificado` é publicado (log do handler, ou consumo da fila `extrator-queue`). Regressão da suíte completa (`pnpm test`) do BC `ingestao-identificacao` e de qualquer teste de integração de `buscarPorId`.

- Ação esperada: corrigir `agregadoDaLinha` em `drizzle-orcamento.repository.ts` para reconstituir `tenantId` a partir de `linha.tenantId`, e devolver para reteste do QA
